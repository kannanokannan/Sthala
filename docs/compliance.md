# Sthala Compliance Posture

Sthala's architecture is designed to align with the following standards
by construction — not by configuration. The on-premise, airgapped deployment
model satisfies the hardest requirements automatically.

---

## Global Standards

### ISO/IEC 42001:2023 — AI Management Systems

| Requirement | Sthala approach |
|---|---|
| Risk management | Egress tiers 1/2/3 enforce data risk classification |
| Transparency | All LLM calls logged with model ID, prompt hash, output hash |
| Human oversight | Egress gate requires human approval before data leaves tier 1 |
| Incident management | Audit log per call; anomaly flags surfaced to operator |

### NIST AI RMF 1.0

| Function | Sthala approach |
|---|---|
| Govern | CLAUDE.md + AGENTS.md define organisational AI policy |
| Map | Recipes declare egress tier and data categories explicitly |
| Measure | OpenTelemetry GenAI semantic conventions; Prometheus metrics |
| Manage | Two-model verification (extraction + cross-check) reduces hallucination risk |

### OpenTelemetry GenAI Semantic Conventions

All LLM calls emit:
- `gen_ai.system`, `gen_ai.request.model`
- `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`
- `gen_ai.response.finish_reason`
- Custom: `sthala.egress_tier`, `sthala.recipe`, `sthala.verification_confidence`

## Regional / Jurisdictional

Country-specific compliance lives in `recipes/<country>/`. The core framework
is country-neutral. Below are the key mappings per recipe region.

### India (`recipes/in/`)

| Regulation | Relevance | Sthala stance |
|---|---|---|
| DPDP Act 2023 | Personal data processing | Tier 1 default — data stays on-premise |
| IT Act 2000 | Data localisation for sensitive data | On-premise satisfies by construction |
| RBI data localisation | Payment data must stay in India | Tier 1 egress — no cross-border transfer |
| GST rules | Audit trail for tax data | Immutable DuckDB log + voucher citations |

### United States (`recipes/us/`)

| Regulation | Relevance | Sthala stance |
|---|---|---|
| AICPA SOC 2 | CPA firm data handling | On-premise = no third-party data processor |
| IRS Pub 4557 | Taxpayer data safeguards | Local-only processing satisfies requirements |
| HIPAA (if clinic) | Health data | Tier 1 egress; PII stays in encrypted local store |

### European Union (`recipes/eu/`)

| Regulation | Relevance | Sthala stance |
|---|---|---|
| GDPR Art. 5 | Purpose limitation, data minimisation | Enforced in pipeline stages |
| GDPR Art. 25 | Privacy by design | On-premise is privacy-by-architecture |
| GDPR Art. 30 | Records of Processing Activities | Auto-generated from audit log |
| GDPR Art. 44+ | Third-country transfers | Tier 1 = zero transfers |
| EU AI Act | AI system classification | Non-high-risk (document management assistant) |

## CycloneDX 1.7 AIBOM

Sthala generates an AI Bill of Materials on each build, covering:
- Model identifiers (HuggingFace repo + commit hash)
- License per model
- Training data provenance (where publicly declared)
- Runtime library dependencies
- Hardware tier declared

AIBOM output: `sthala-aibom.json` (generated by `install.sh --aibom`)

## Audit Log Schema

Every LLM call and egress action is logged:

```json
{
  "ts": "2026-05-23T10:15:00Z",
  "recipe": "in/tally-ca-copilot",
  "stage": "extract",
  "model": "sarvam-30b-q6k",
  "input_hash": "sha256:abc123...",
  "output_hash": "sha256:def456...",
  "egress_tier": 1,
  "verification_confidence": 0.91,
  "human_approved": null,
  "pii_detected": false
}
```

Log is append-only. No raw data in log — only hashes and metadata.

## What Sthala Does NOT Handle

- Legal advice on compliance (consult your DPO / legal counsel)
- Certification audits (Sthala is a technical framework, not a compliance service)
- Country-specific rules outside the listed regions — add a new `recipes/<country>/` folder
